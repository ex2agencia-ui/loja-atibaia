## O que foi implementado hoje (2026-07-28)

### Correções de bugs (Neon HTTP)

Operações `updateMany`, `deleteMany` e `createMany` disparam transação implícita no Neon HTTP serverless e causam erro `Transactions are not supported in HTTP mode`. Corrigidos:

| Arquivo | Operação problemática | Correção |
|---|---|---|
| `src/app/api/comunicados/[id]/lido/route.ts` | `updateMany` | `findMany` + `Promise.all(update)` |
| `src/app/api/comunicados/[id]/route.ts` | `updateMany` | `findMany` + `Promise.all(update)` |
| `src/app/api/membros/[id]/route.ts` | `deleteMany` + `createMany` (filhos) | `findMany + Promise.all(delete)` + `Promise.all(create)` |
| `src/app/api/membros/route.ts` | `createMany` (filhos) | `Promise.all(create)` |

**Regra geral:** nunca usar `xxxMany` nem `create({ include })` — sempre separar em operações individuais com `Promise.all`.

## Contexto técnico importante

### Next.js 16.2.4 com Turbopack
- Sem `middleware.ts` — proteção feita em cada route/page via `auth()`
- Server Components usam `auth()` diretamente
- Client Components recebem role/dados como props — **nunca `useSession`** em page-level
- `searchParams` é `Promise<{...}>` — sempre `await searchParams`

### Neon HTTP serverless
- **Nunca**: `createMany`, `updateMany`, `deleteMany`, `create({ include })`, `prisma.$transaction()`
- **Sempre**: operações individuais com `Promise.all([...items.map(i => prisma.model.create(...))])`

### Auth pattern
```typescript
// Server Component / Route Handler:
const session = await auth()
const user = session?.user as { id?: string; role?: string; memberId?: string }

// Client Component: recebe role como prop do server component pai
```

### Monetary values
- Sempre `Decimal` no Prisma/PostgreSQL
- Sempre `Number(value)` ao usar em JS (não `parseFloat(value.toString())`)
- Nunca `Float`
